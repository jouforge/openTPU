# AMD Alveo V80 port

The `port/v80` branch adds the AMD Alveo V80 as an openTPU target using the existing ISA,
compiler, model implementations and tools. The AMR-based single-slice image has passed
routed timing, segmented PDI/XSA export, matching AMC generation and real-card qualification.
Qwen3.5-0.8B INT8 prefill and successive decode match the same target's ISA simulator bit
for bit over eight prompts and 128 generated steps. The qualified baseline runs the core
at 100 MHz with a related 200 MHz pumped-memory clock and exposes 32 GiB of tested HBM.

Build and runtime instructions are in [boards/v80/README.md](../boards/v80/README.md).
The dated qualification below identifies the exact images, checks and remaining limits.

The `feat/fp16` branch additionally qualifies the explicit `v80:fp16` variant:
native W16A16 matrices with FP32 accumulation, full dense Qwen3.5-0.8B text
inference and preservation of the existing INT8 path. See the [FP16 qualification](fp16.md#complete-v80-implementation-2026-11-14)
for its distinct image, resource/timing results, numerical checks and measured
performance. It uses the same 100/200 MHz clocks and local Tcl build flow.

The `feat/mixed-precision` branch qualifies `v80:mixed`: packed signed INT4 tile
decoding and explicit W16A16/W8A8/W4A16 matrix selection within dense Qwen3.5.
The [2026-11-15 mixed-precision qualification](mixed_precision.md#v80-deployment-and-validation-2026-11-15)
records complete board/model checks, cold/warm loads and performance. Full W4A16
has visible quantization loss and is slower than W16A16 in the initial schedule;
the original automatic/INT8 default is preserved.

## Official board references

Use the [AVED documentation](https://xilinx.github.io/AVED/latest/index.html) for platform
architecture and [DS1013](https://docs.amd.com/r/en-US/ds1013-v80/) for physical card details.
Reviewed on 2026-11-13: AVED's `latest` page describes the 2025.1 tool release. It is not
the build specification for this port's AMR/2026.1.1 baseline; release-specific build and
packaging commands must come from the selected platform.

- The [HBM map](https://xilinx.github.io/AVED/latest/AVED%2BV80%2B-%2BMemory%2BMap.html)
  covers `0x4000000000..0x47ffffffff`: 32 pseudo-channels of 1 GiB. The openTPU mapping
  groups four adjacent pseudo-channels per logical channel; the base address is added once.
- [DS1013 clocking](https://docs.amd.com/r/en-US/ds1013-v80/Clocking) specifies two 200 MHz
  HBM reference clocks. These are separate from the overlay's 100 MHz AXI/core and related
  200 MHz core clock; they do not establish achieved HBM bandwidth.
- The [NoC guide](https://xilinx.github.io/AVED/latest/AVED%2BV80%2B-%2BNoC%2BConfiguration.html)
  describes dedicated HBM NMUs and the cost of non-direct memory access. The initial eight
  AXI ports provide functional integration; bandwidth tuning requires measured traffic and
  physical NoC placement, not just the card's advertised bandwidth.
- The [reset guide](https://xilinx.github.io/AVED/latest/AVED%2BV80%2B-%2BClock%2BReset%2BModule.html)
  requires a coordinated whole-device reload for NoC/PS/memory reset. PCIe or PL reset alone
  does not restart that system. Preserve the bridge's drain behavior and boot-once AXI state.
- The [AVED build flow](https://xilinx.github.io/AVED/latest/AVED%2BBuild%2BScripts.html)
  distinguishes the hardware XSA/PDI, AMC firmware, Design PDI and FPT Setup PDI. A routed
  checkpoint or raw hardware PDI is not a deployment image. Packaging must use matching
  hardware/firmware and the installed management/FPT scheme. The local flow includes gated
  hardware-image export; it does not write flash or change the
  card's boot partitions.

## Names

Existing board directories use lowercase model identifiers: `bcu1525` and `ypcb-00338`.
The V80 follows the same convention:

| Item | Name |
|---|---|
| Board identifier | `v80` |
| Prose | AMD Alveo V80 |

| Board build flow | `boards/v80/` |

| Board documentation | `docs/v80.md` |
| Versal cell family | `xilinxversal`, in `rtl/tech/xilinxversal/` |
| Default generated-output directory | `build/vivado_v80/` |

Keep the `otpu_` prefix and lowercase underscore-separated RTL module names used by this
repository. A module's file has the same name, for example `otpu_fpga_top_v80.sv`.
Python modules and tests use lowercase underscores too, for example `qdma.py` and
`test_v80.py`. The cell family follows `xilinx7` and `xilinxus`; it describes the device
architecture and can serve other Versal boards.

Use `v80:<variant>` for later arch/uarch alternatives within the same platform mapping.
Introduce a separate target such as `v80-s2` only when a distinct machine topology or board
integration warrants it, following the BCU1525 targets. Such targets still share the
`boards/v80/` and `rtl/boards/v80/` directories. A clock-only build override does not need a
new board name. Qwen model names, AMR versions and hostnames do not become target suffixes.

## Integration contracts

**Target configuration.** The target is based on the single-slice
`bcu1525-wg:kt` architecture: D 128, MCOLS 8, WG 8, AW 36, with platform ID 8 and `xilinxversal`
cells. Its relative memory map has eight logical channels of 4 GiB and 128-byte
beats. The platform boundary maps these to 32 HBM pseudo-channels, four per logical channel;
all 32 GiB passed the final hardware memory tests below. BHW is 0.
The BCU1525's MIG address mapping and physical constraints do not describe V80 HBM.
CFG_HASH describes the ISA configuration, not the board: `v80` and `bcu1525-wg:kt` have the
same initial hash (`d49b52f5`), while their platform IDs and technology selections differ.
Derive RTL parameters and
source lists through `opentpu.target`; the board's configuration registers and the host's
checks must describe that same machine.

**Memory addressing.** Define the core's relative DRAM address, logical-channel mapping
and each host/PL NoC address view together. The inspected platform maps HBM at
`0x4000000000`. A 36-bit core address can represent offsets within 32 GiB, but cannot carry
that absolute base. Extend the address before translating at the bridge/transport boundary;
derive each view from the platform address map. Host-loaded weights and PL reads must reach
the same physical bytes. Advertise only the capacity that the implemented mapping exposes
and the board qualification covers.

**Memory protocol.** `otpu_v80_mem` reuses `rtl/mem/otpu_hbm_ch.sv`: one ID, at most
16 transfers of 256 bits, INCR, no 4 KiB crossing. It extends AxLEN to 8 bits, supplies AXI4
sidebands and adds the absolute HBM base to the widened channel address. The existing bridge
retains byte strobes, read/write hazards, B-confirmed native write completion, posted reads,
half-beat responses and core-reset draining. Nonzero response IDs latch an error.

**Readiness and reset.** The baseline boundary does not export a PL HBM calibration flag.
A read-only startup probe of each of the four PCs in each logical channel must finish with
OKAY, ID-zero, single-beat responses before that channel contributes to STATUS CALIB0/1.
Those flags aggregate even/odd channels, as in the shared shell. They indicate successful
route responses, not PHY telemetry or complete memory qualification. Missing responses keep
readiness low; failed responses latch AXI error. Probes never write memory.

AMD's [NoC reset contract](https://docs.amd.com/r/en-US/pg313-network-on-chip/Resets)
allows PMC power-on/DFX resets and provides no user-routable reset to NoC AXI ports.
The physical top therefore releases the AXI state once after configuration and keeps it
through later PL-only resets. The core side resets and drains through the existing bridge;
it must not discard outstanding NoC responses. Retrying startup probes requires coordinated
PL/NoC reconfiguration. Qualify the AMR load/reload sequence before enabling deployment.

**Clocks.** Versal `clk_wizard` generates phase-aligned 100/200 MHz outputs from one MMCM.
CIPS PL0 remains the 100 MHz AXI clock. PF1 SmartConnect crosses CSR into the core clock;
the core reset waits for MMCM lock. `check_bd.tcl` checks actual MMCM dividers/phases as well
as the address map. Do not declare the 1x/2x clocks asynchronous to conceal timing failures.

**Host access.** `QdmaTransport` implements the existing Board transport operations. PF1
BAR2 + `0x100000` is a 1 MiB openTPU CSR window, translated to `0x20200100000` in the NoC;
AMR management, QDMA configuration and AMR GPIO at BAR2 + `0x20000` remain separate.
The explicit selector is `qdma:0000:bb:dd.1@queue`; the transport requires an existing
bidirectional MM queue and shares one device lock across every queue of the PF. Registers
use native 32-bit MMIO, with monitor writes limited to SNAP. Synchronous QDMA reads/writes add
the HBM base to Board's relative channel addresses once. Host/core streaming stays disabled
until concurrency qualification; this is independent of the ISA target's STREAM capability.

**Technology cells.** `xilinxversal` implements the three common arithmetic cells with
DSP58 primitives, preserving interfaces, enabled-edge latency and the ISA numerical
contract. Generic models remain the simulation reference. The initial generic synthesis
provides a resource baseline; compare the explicit mapping after implementation.

## Versal cells and implementation

On 2026-11-13 the V80 board RTL/testbench declarations were aligned with the existing
openTPU board style. The archived pre-edit and post-edit sources have identical token
streams after removing whitespace and comments. Physical AMR port names remain the names

the column end uses full 58-bit internal cascades and exposes the existing low 48-bit

the common 48-bit interface cannot carry the native 58-bit PCOUT/PCIN bus. An initial
partial-cascade mapping passed simulation but failed post-opt DRC with DPCA-12; it was
rejected before completing placement. Native cascade ports must be connected in full
([AMD DSP58 ports](https://docs.amd.com/r/en-US/ug1485-versal-architecture-premium-series-libraries/DSP58)).
The P/C mapping preserves the common RTL and pipeline, at the cost of fabric routing;
the qualified implementation meets timing with those links. Packed products, the rounding
bias, enabled-edge registers, stalls and row accumulation retain the generic contract.
The 21 pre-existing target/variant snapshots
remain unchanged; V80 keeps CFG_HASH `d49b52f5` and now selects `family = "xilinxversal"`.

`tools/tech_dsp.py` uses the installed Vivado UNISIM library and runs both the generic
and vendor cells in XSim with identical stimulus. Both testbenches passed with Vivado
2026.1.1 for seeds 3, 7 and 11, each with 3984 compared cycles. The DSP bench checks all

The same benches also passed with the official DSP48E1 and DSP48E2 models.

## Implemented constraints and acceptance

The flow generates `amr.pins.xdc` from AMD's physical pin file, replacing exactly four
reversed HBM reference-clock assignments in that local copy. Other lines and the external
source stay unchanged; the generated file is hashed in the manifest. The local XDC assigns
P/N to N19/N18 (bank 800) and N37/N38 (bank 801). Vivado's package database identifies these
as C4CCIO_PAD0/P and C4CCIO_PAD1/N, as specified in
[PG313](https://docs.amd.com/r/en-US/pg313-network-on-chip/Clocking).
The implementation gate checks these four actual package pins after routing.

The board flow replaces AMR's stale hierarchy/floorplan constraints locally and reuses
`otpu_hbm_ch.tcl` and `otpu_clk2x.tcl` from the existing board flows. These cover FIFO Gray
pointer datapath delay and bus skew, and pumped TMEM requests/results with the RTL's
enabled-edge multicycle contract. `otpu_v80_top.tcl` also constrains the posted-beat counts
and status crossings outside the bridges. The readiness probe registers its completion
level before the calibration synchronizers. Missing constraint coverage fails before
optimization. Pumped MXU configurations are rejected because the shared MXU constraints
target DSP48E2 pins; this V80 target uses an unpumped MXU.

`make impl` saves routed utilization, clock, timing, CDC, bus-skew, DRC, I/O and primitive
reports plus a checkpoint before checking acceptance. Incomplete/error routes, negative
setup/hold/pulse-width or bus-skew slack, unsafe/unknown CDC endpoints, missing ASYNC_REG,
DRC errors/critical warnings or incorrect HBM clock pins fail the command. Bus skew needs
its own report; it is not included in the timing summary
([UG903](https://docs.amd.com/r/en-US/ug903-vivado-using-constraints/About-Bus-Skew-Constraints)).
`make pdi` applies the same gate before exporting segmented images and the implemented XSA.

## Chat performance and caches — 2026-11-14

The same 100 MHz image was profiled on qfpga0 with Qwen3.5-0.8B INT8, the default
2048-token context capacity and sampler, seed 42, and a 64-token output limit. The
prompt was `请用中文介绍一下你自己。` (17 tokens after the chat template). OMP and MKL
thread counts were both 8. No RTL, target parameters or runtime source were changed.
Use the [cache setup and chat command](../boards/v80/README.md#run-qwen35-with-caches)
to reproduce the workload on a provisioned board.

| Run | Model load | TTFT | Wall decode | Device decode |
|---|---:|---:|---:|---:|
| No disk caches, first prompt | 11.2 s | 54.43 s | 11.88 tok/s | 20.1 tok/s |
| Same process, reset and repeat | already loaded | 0.22 s | 20.05 tok/s | 20.1 tok/s |
| Empty disk caches, first prompt | 13.0 s | 54.84 s | 20.01 tok/s | 20.1 tok/s |
| New process, populated disk caches | 5.4 s | 0.67 s | 20.01 tok/s | 20.1 tok/s |
| Plain CLI with populated caches, without timing wrappers | 5.9 s | 0.57 s | 20.00 tok/s | 20.1 tok/s |

The reset comparison reuses the engine's programs and clears conversation state; it
does not reset the sampler's RNG. Each new process starts with seed 42. These short
performance runs supplement the separate bit-exact model qualification above; they
do not establish long-context speed, model quality or throughput for other models.

The uncached load spent 1.48 s reading weights, 6.99 s constructing the memory image,
and 1.39 s writing the image to the board, with the remainder in initialization.
With the image cache populated, image retrieval took about 0.3 s; weight loading,
initialization and transfer to the card still take time.

The first prompt waited 54.13 s in prefill coverage/fit preparation. The background
thread prepared 80 candidate programs: their compilation took about 9.13 s and
`waits.entries()` about 44.69 s. The wait tables encode instruction dependencies for
the sequencer. `prefill.warm()` starts in the engine constructor, and an early prompt
waits on the same lock; time spent typing can therefore shorten the observed TTFT.
The actual 17-token prefill's device cycles correspond to about 0.19 s.

The uncached first decode also spent 0.12 s compiling its generate program and 2.04 s
preparing its wait table, after the first token. The CLI includes that time in its
average decode rate. In the populated-cache process there were 22 program/fact disk
hits and 21 wait-table disk hits, with no compilation or wait-table computation.
The program cache also enables the existing background generate-program warmup,
which explains why the first decode in the empty-cache run was already fast.

The observed chat path used the on-card generate loop (`on_card=True`), including
sampling after the first token. QDMA's `streams=False` disables the streamed-logit
path; it does not disable this generate loop, whose token polling is a separate path.
The first reply's wall/device rate gap therefore does not establish a fixed per-token
host sampling or full-logit transfer cost. Warm decode measured about 4.97 million
cycles per token at 100 MHz, closely matching its wall rate. Improving that steady
rate requires investigating the device's execution cycles and clock, independently
of cache setup.

Timing wrappers recorded nested main/background-thread calls; their inclusive times
overlap and must not be added together. Raw logs, JSON timings and the diagnostic
wrapper remain in local `build/vivado_v80/performance_20261114/`; on qfpga0 the
corresponding directory is `/home/pqq/workspace/openTPU-v80-build/perf-investigation-20261114/`.

ERROR / AXI_ERR / ECC_DED. No new hardware build was needed for this comparison.


## Commit sequence and acceptance

Each stage should be reviewable on its own. A registered target may be simulation-only
before board integration is complete; state that status explicitly. Model availability
does not imply that a new board has passed hardware qualification.

| Stage | Changes | Acceptance |
|---|---|---|
| 0. Naming and layout | this plan, board README and link from the target documentation | local links resolve; planned files are distinguished from implemented support |
| 1. Target and simulation | `v80.toml`, target registration and configuration tests | target loads; source lists resolve; existing target hashes stay stable; applicable config/model tests pass |
| 2. Platform and transport | AMR/Tcl flow, CSR integration, QDMA transport and memory bridge | offline and protocol tests pass; CSR access and host/PL cross-read/write tests agree across the advertised address space |
| 3. Core and technology | complete single-slice integration; DSP58 mapping if needed | ISA/RTL checks pass; synthesis and implementation pass timing, DRC and clock/reset review |
| 4. Model qualification | Qwen3.5-0.8B text bring-up using the existing tools | prefill, successive decode and reset pass; card logits match the same target's ISA simulator bit for bit |
| 5. Capacity and performance | larger models, more memory concurrency and measured tuning | complete model image fits; sustained bandwidth and device/wall throughput are measured with configuration recorded |

The agreed branch sequence is:

1. `port/v80`: physical board/model qualification, generated local Tcl and recorded build
   inputs, followed by reproducible deployment, cache setup and cold/warm performance
   records. Keep the qualified baseline available by Git revision.
2. `feat/fp16`: native FP16 arithmetic across the ISA, simulator, compiler, RTL and runtime,
   through a complete model. Define accumulation precision, rounding, exceptional values
   and numerical acceptance first; then validate an individual matrix operation before
   model integration. BF16 is an extension to evaluate, not a replacement for FP16.
   Reading a floating-point checkpoint and quantizing it to the current format does not
   fulfill native FP16 support.
   The [FP16 numerical contract and integration checks](fp16.md) track this branch's
   arithmetic and instruction/compiler stages separately from full board/model qualification.
3. `feat/mixed-precision`: W16A16/W8A8/W4A16 selection within a model, including weight
   encoding, activation and accumulation precision, conversions and per-operator dispatch.
   Validate each mode and the boundaries between them. Existing per-layer weight-format
   selection can be reused but does not itself supply a 16-bit activation compute path.
   Report model quality, throughput and memory separately from hardware/ISA agreement.
   The [mixed-precision contract and integration gates](mixed_precision.md) track this work.
4. `perf/v80`: optimize the completed precision paths. Compare generic/DSP58 mapping and
   LUT/DSP/BRAM/URAM use, improve data supply, then tune clocks and array size through
   separately measured changes. Generic inference does not guarantee fewer DSPs; choose
   by routed timing, resource limits and real-card throughput rather than equal resource
   percentages. Preserve numerical behavior and record results per precision mode.

Each branch builds on the preceding accepted revision. Cache fixes, timing breakdowns
and counter/trace measurements support every stage; major resource restructuring,
frequency tuning and scaling remain in the fourth branch. Native FP16 is qualified
in `feat/fp16`; W4A16 and explicit mixed policies are qualified in
`feat/mixed-precision`, independently of the existing 4/8-bit format survey.
Keep the openTPU
source layout and RTL conventions as each implementation is added.

Keep tests with the implementation they validate. Use the existing `tools/validate.py`,
`otpu-selftest`, `otpu-diag` and profiler paths as support is added. HF comparisons evaluate
quantization quality separately from the card/ISA bit-exactness requirement.

Generated results live under `build/vivado_v80/` (or the selected `OUT_DIR`): projects,
checkpoints, PDI/XSA products, reports and run manifests. Record the openTPU revision and
local changes, target/CFG_HASH, platform dependency revisions, tool version, source IP
identity and artifact hashes. Add concise, reproducible qualification results to this
document when available. Build scripts must be runnable without a live MCP session;
interactive investigation should become checked-in Tcl or runner changes before it is
part of the supported flow.
