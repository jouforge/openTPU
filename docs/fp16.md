# FP16 computation

The `feat/fp16` branch adds a binary16 operand path with FP32 accumulation. Its
numerical foundation is `opentpu/fp16.py`, the binary16 functions in `otpu_fp`, and
the native `otpu_hmul` / `otpu_hmadd` pipelines in `otpu_fpipe.sv`. This document
defines their contract and the instruction/compiler integration. A V80 image from
`port/v80` does not acquire FP16 support by checking out this branch or importing
these functions. FP16 is an explicit, default-off hardware capability; complete
V80 image and model qualification remain separate gates.

## Numerical contract

- Operands are IEEE binary16: one sign bit, five exponent bits, ten fraction bits,
  exponent bias 15. Packed memory words are little-endian uint16 values.
- FP32 to FP16 conversion rounds to nearest, ties to even. It preserves gradual
  underflow in FP16, including signed zero, and overflows to signed infinity.
  Every NaN becomes the positive quiet NaN `0x7e00`; there are no exception flags.
- FP16 to FP32 is exact for every finite encoding, including FP16 subnormals.
  Signed zero and infinity keep their signs; every NaN becomes `0x7fc00000`.
- A finite FP16 product is computed directly from its two 11-bit significands.
  It has at most 22 significant bits and lies in the normal FP32 range when
  nonzero, so the FP32 product is exact. There is no intermediate FP16 rounding.
  Multiplication uses XOR signs, including zero; NaN inputs and infinity times
  zero produce canonical FP32 NaN.
- Addition to the FP32 accumulator uses the existing `fp_add` contract: RNE, FTZ
  for FP32 input/output subnormals, canonical NaN, and the existing signed-zero
  rules. FP16 subnormals are preserved because they widen to normal FP32 values.
- Each matrix output starts at positive zero, or the supplied FP32 accumulator,
  and accumulates products in increasing K order. An empty reduction returns
  the initial accumulator unchanged. Parallel lanes may compute independent
  outputs; a different reduction tree requires an explicit numerical change.
- Results remain FP32 until an explicit conversion boundary. W16A16 describes
  the matrix operands, not the accumulator or every other model operation.
  Rounding activations to FP16 before each matrix is part of model integration;
  multiplying FP32 activations by widened FP16 weights is not W16A16.

BF16 uses a different exponent/fraction split and is outside this first contract.
Existing INT8/4-bit MX arithmetic, FP32 operations and ST16 state formats retain
their current semantics.

## Arithmetic pipelines

`otpu_hmul` takes binary16 `a` and `b` and produces an FP32 product. Its latency is
two enabled edges by default, with optional output delay (`LAT >= 2`). The first
stage multiplies 11-bit significands and records operand classes and exponent;
the second normalizes and selects finite/zero/infinity/NaN output.

`otpu_hmadd` takes binary16 `a`, `b` and FP32 `c`. It delays `c` beside the product
and uses the existing pipelined FP32 adder. Latency is `LM + LA`, with `LM >= 2`
and `LA >= 4`. Both units accept an independent input on every enabled edge;
`en=0` freezes all stages. Like the existing FP32 pipelines, payload registers
have no reset or valid signal; the enclosing execution unit owns validity,
reset cancellation and output backpressure.

`otpu_hdot` connects N such lanes to FP32 accumulators. One accepted beat supplies
one activation and N weights; consecutive beats traverse K, giving one row of
`A @ B` at `last`. `first` selects the initial FP32 seed, which is positive zero
for a non-accumulating matrix operation. N lanes compute distinct outputs rather
than partial sums, preserving the specified K order. A new row must start with
`first`; an unfinished row must not start again without reset.

This initial controller keeps one beat in flight, accepting a non-final beat
every `LM + LA + 1` cycles (seven at the defaults). Input gaps do not advance the
dot product. Final results are held until `out_ready`; reset cancels both pending
arithmetic and held results. Empty K is handled outside this component. The
controller prioritizes a simple numerical/protocol baseline; it is not a claim
of the full throughput of its pipelined arithmetic or of model performance.

## Packed operands and compiler interface

`HMM` (0x23) and `HCVT` (0x24) operate on TMEM through `otpu_hmxu`.
[The ISA](isa.md#hmm-and-hcvt) specifies their fields, bounds, footprints and
zero-size behaviour. `Config.FP16` / RTL `FP16` enables them; CAPS2 bit26 announces
them. ULANES must be a power of two, at least two. Older target hashes are unchanged
when FP16 is off, and older images advertise no FP16 support.

The first integration shares the MXU's ports and execution slot, serializing that
slot when FP16 is enabled, including integer MM commands. A half command waits for
the sequencer's TMEM release, separately from integer weight prefetch. The read
adapter retains each request until accepted, handles TMEM's automatic conflict
replay, and returns the delayed result once. Output writes wait for the arbiter's
grant. The controller holds one memory read at a time and feeds one ordered
K beat to `otpu_hdot`; its memory/control overhead is additional to the arithmetic
latency. This is a functional baseline, with no model throughput claim.

The kernel language exposes explicit format boundaries:

```python
from opentpu import language as ol
from opentpu.runtime import HalfInput, Input, Output, launch

@ol.jit
def linear(x, w, out):
    a = ol.pack_fp16(ol.load(x))
    b = ol.load_fp16(w)
    ol.store(out, ol.matmul_fp16(a, b))

# cfg.FP16 must be True. a is [M, K], b is [K, N].
result = launch(linear, cfg, x=Input(a), w=HalfInput(b), out=Output((M, N)))
```

`HalfInput` rounds host FP32 values once and stores binary16 rows with a zero
padding halfword for odd widths. `load_fp16` moves these packed words directly
through DMA. `HalfTensor` views support word-aligned row/column slices and affine
loop addresses. `HalfTile` owns a packed TMEM allocation and is distinct from a
FP32 `Tile`; `unpack_fp16` explicitly expands it for VPU work. `matmul_fp16` takes
two 2-D HalfTiles and optionally updates an FP32 `acc` tile in place, preserving
its compiler version and dependencies. These language APIs operate on tiles that
fit TMEM; the tiled kernels below compose them for larger matrices. Model engine
prefill/decode lowering remains to be implemented. No model CLI FP16 weight-format
option is advertised yet.
`store_fp16` writes packed tiles through DMA and requires even logical row
widths: an odd-width subview must not overwrite a neighbouring halfword.
Contiguous even-width tiles can convert with one HCVT when their total element
count fits its 16-bit count field; otherwise conversion proceeds row by row.
The experimental `v80:fp16` target enables the hardware at the existing 100 MHz
target clock; `v80` remains the qualified default. The variant is a build/input
configuration, not a claim that its complete board image has passed qualification.

### Tiled projections and SwiGLU

`opentpu.kernels.fp16.matmul(a, b, out, block=(4, 32, 32))` operates on DRAM
matrices `[M,K] @ [K,N] -> [M,N]`. `a` can be FP32 or packed binary16, `b` must be
packed binary16, and `out` is FP32. The block sizes are M, N, K; N/K blocks must
be even for word-aligned packed views. Each dimension's full tiles use a hardware
loop and its short tail uses its actual size. K accumulates into the same FP32
tile throughout; no tree reduction or half-rounded partial sums are introduced.
The default working set fits the test configuration's 4,096-word TMEM; callers
with other live tiles must leave room for it. Three loop levels are needed for
fully tiled matrices, within the compiler's four-level limit.

`HalfWeight(w, shard=None)` accepts checkpoint-style `[N,K]` weights and stores
their transpose as word-padded binary16 `[K,N]` once at placement. `shard=0`
partitions N evenly across slices (each local row padded independently); there
is no K sharding, which would change accumulation order. Its DRAM allocation
honours `place(..., weights_at=...)`. `HalfInput` remains an already-oriented
matrix input. Both descriptors are `HalfTensor`; neither consumes an integer
MXU weight-format encoding.

```python
from opentpu import language as ol
from opentpu.kernels.fp16 import matmul
from opentpu.runtime import HalfWeight, Input, Output, launch

@ol.jit
def projection(x, w, out):
    matmul(x, w, out)

# x [M,K], checkpoint weight w [N,K]; cfg.FP16 must be True.
result = launch(projection, cfg, x=Input(x), w=HalfWeight(w), out=Output((M, N)))
```

Inputs may alias each other, but output bounding ranges must be provably disjoint
from both inputs, including row gaps. Affine DRAM views work when those bounds
can be proven, including the full range of static-count hardware loop terms;
unknown run-time loop bounds are rejected. Host `Output` base/offset must be
static at the kernel call. The
kernel records the complete written rows once for runtime collection, separately
from the loop-dependent ST instructions. Padding is not declared written.

`swiglu(a, w_gate, w_up, w_down, out, scratch)` adds the complete dense MLP's
three projections, FP32 SiLU and FP32 elementwise product. Two caller-owned
FP32 DRAM scratch matrices `[M,F]` hold the gate/up intermediates; the gate
scratch is then overwritten with `SiLU(gate) * up`. The down projection rounds
that product to binary16 on the device. Scratch and output must be disjoint from
each other and all inputs. Normalization, residuals, attention, recurrent state
and multi-slice communication remain the model caller's responsibility.

This first schedule prioritizes bounded memory and exact arithmetic. It reloads
activation tiles for each output-column tile and weights for each row tile, and
uses row DMA loads for the K-major weights. It makes no throughput claim; weight
blocking, reuse and overlapping transfers belong to subsequent optimization.

### Packed-cache attention and Qwen3.5 attention image

`opentpu.kernels.fp16_attention.attend` accepts Q `[M,D]` in FP32 or binary16,
binary16 K-transpose `[D,T]`, binary16 V `[T,Dv]`, FP32 output `[M,Dv]` and FP32
score scratch `[M,T]`. The numerical sequence is explicit:

1. Round Q to half, accumulate QK in increasing D order, then multiply the FP32
   scores by `1/sqrt(D)`.
2. Apply an optional mask with MIN (`+inf` valid, `-inf` masked). Every query must
   have at least one valid token; Q/K/V operands must be finite. Views must stop
   at initialized cache tokens.
3. Compute stable FP32 softmax as `exp2((score - max) * log2(e))`. The denominator
   uses the existing VPU interleaved sum within each `softmax_block` (default 32),
   then adds chunk sums in token order. The block size is part of the arithmetic
   contract; it is not a promise of identical results under arbitrary regrouping.
4. Store normalized FP32 probabilities in scratch, round them to binary16 at
   the P.V boundary, and accumulate P.V in increasing token order with FP32 carry.

Score scratch bounds the TMEM working set; this schedule does not repeatedly
rescale already rounded probability tiles. It does read/write scratch several
times and makes no bandwidth or performance claim. Output/scratch ranges must
be disjoint from each other and all inputs.

`append` takes FP32 key/value rows. V is packed and stored as one token-major
row. K updates one column of its transposed cache by reading the containing
pair of halfwords, replacing the selected column and writing the pair back.
Cache capacity and V width must be even; cache storage must be initialized,
and the append position is currently static. Preserving the neighbour prevents
an odd token from destroying the preceding token. Cache arithmetic assumes
finite values; noncanonical NaN payload preservation is not a cache contract.

`opentpu.llm.qwen35_fp16.AttentionImage` is an experimental **single attention
sublayer** image for S=1. It places packed projection weights, gains, FP32
scratch and persistent FP16 KV caches. Its program includes input RMSNorm,
Q/K/V projections, per-head Q/K RMSNorm, partial RoPE, grouped-query attention,
sigmoid output gating, output projection and residual addition. Gains follow
Qwen3.5's `1 + weight` convention. Per-head K-transpose blocks are `[D,cap]`,
V blocks `[cap,D]`; both use even row widths. No INT8 KV cache or QACT is used.

`compile(pos)` specializes a fixed number of rows at a static position.
`inputs(images, x, pos)` updates only input activations, RoPE tables and the
causal mask. Cache state stays in the returned DRAM images across runs. The
caller must supply all preceding cache positions. This class is not wired into
the full-model Engine, CLI, or image/program disk caches yet; there is no
full-model FP16 format option or board qualification implied by this image.

## Validation

`tests/test_fp16.py` checks all 65,536 binary16 encodings, every finite positive
conversion interval's midpoint and FP32 neighbours with both signs, random FP32
encodings, special-value products, cancellation and seeded matrix accumulation.
NumPy conversions and float64 products provide independent reference checks;
the model does not use a host BLAS reduction whose accumulation order may differ.

The RTL vectors exercise conversions, native multiply and multiply/add at both
default and extended pipeline latencies, with enable stalls and changing payloads.
The matrix-stream checks exercise N = 1, 8 and 3 outputs, K = 1, 2, 7, 16, 65 and
129, seeded accumulation, input gaps, output backpressure and reset at every
pipeline position, including a held result. They compare each output with the
ordered Python matrix reference.
Run with the project's Python environment and supported Verilator on `PATH`:

```sh
python -m pytest -q tests/test_fp16.py
python -m pytest -q tests/test_fp.py
```

`tests/test_fp16_isa.py` checks DMA/conversion/matrix/store programs with integer
MM interleaving, register-relative addresses, both sequencers and the V80 pumped
TMEM settings. The contention test requires a nonzero MXU-port replay count while
the VPU runs; all TMEM and DRAM words must match the reference. Edge tests cover
odd tails, multiple output tiles, zero dimensions, K=0 seed-bit preservation,
special conversions and capability-off rejection before any write.
`tests/test_fp16_compiler.py` checks packed host storage, conversion boundaries,
matrix accumulator/VPU ordering (including draining obsolete fused row sums),
loop addresses, split-K accumulator carry and rejected types/layouts. Its native
memory case derives the full architecture/channel/microarchitecture settings
from `v80:fp16`, reducing only TMEM, IMEM, ACT depth and the DRAM image size. It
uses eight 128-byte channels, 36-bit addresses and random memory stalls. This is
the functional native-memory model, not physical HBM or a bandwidth measurement.

```sh
python -m pytest -q tests/test_fp16_isa.py tests/test_fp16_compiler.py
```

`tests/test_fp16_tiled.py` adds matrices larger than TMEM, hardware-loop tails in
all dimensions, strided views and untouched output borders, packed padding,
special values, output-column sharding, high weight placement, overlapping
storage rejection and full SwiGLU arithmetic. RTL checks cover both sequencers,
V80 native memory with random stalls, and the MLP's conversion/VPU boundaries.
Large 256-row 1024→3584 and 3584→1024 projections compile to the same instruction
count and TMEM footprint as full tiles of small matrices; dimensions only change
loop counts. Run the complete instruction/kernel gate with:

```sh
python -m pytest -q tests/test_fp16_isa.py tests/test_fp16_compiler.py tests/test_fp16_tiled.py
```

## Integration gates

The arithmetic and instruction/compiler commits are intermediate boundaries,
not the completion of `feat/fp16`. Progress and remaining gates are:

1. Implemented: instruction and packed operand layouts, reference execution,
   address bounds and read/write footprints, without repurposing MM format bits.
   Integer/FP16 interleaving and TMEM contention are covered by integration tests.
2. Implemented in simulation: native execution connected to memory and dispatch,
   capability advertisement and rejection on older images. FP16-disabled target
   identities remain stable. Full-image qualification must also exercise run/reset
   cancellation with the physical memory and host interface.
3. Implemented: basic tile APIs, automatic M/N/K tiling with hardware loops,
   packed FP16 weight placement/output-column sharding, and dense SwiGLU kernels.
   K carries FP32 sums in increasing order; each matrix rounds activations at its
   W16A16 boundary. Full-size checkpoint MLP arithmetic is checked in ISA simulation.
   Also implemented: packed KV append, native attention, and one complete
   Qwen3.5 gated-attention sublayer image, with persistent-cache RTL checks and
   full-size checkpoint-weight ISA checks. Remaining: DeltaNet and the complete
   model image/Engine path. No per-layer host conversion or FP32 matrix fallback qualifies.
4. Integrate prefill and decode, compare layer results and model logits against the
   ordered FP16 reference, and measure the quality difference from the original
   checkpoint separately from RTL correctness. Cache keys must distinguish the
   new precision, layout, program ABI and target capability.
5. Route the complete V80 design, qualify the resulting image, and run the full
   Qwen3.5 model on the card. Record numerical checks, resource/timing results,
   cold/warm load, TTFT and device/end-to-end throughput before closing the branch.

Mixed precision follows this complete native FP16 path. Its W4A16 multiplication
and precision boundaries need their own numerical contract; the current INT4
weight path with quantized activations does not already provide W4A16.
